# Архитектура и инфраструктура Knowledge Hub

## Назначение

Документ описывает текущее состояние репозитория, целевую инфраструктуру MVP и рекомендуемые параметры VPS. Компоненты отмечены как имеющиеся сейчас или планируемые: целевая схема не означает, что все сервисы уже реализованы в коде.

## Состояние репозитория

На момент подготовки документа в проекте есть базовый Django-проект и Docker Compose для Django и PostgreSQL:

- Django и PostgreSQL-драйвер перечислены в requirements.txt.
- docker-compose.yml запускает PostgreSQL и Django; данные PostgreSQL хранятся в именованном Docker volume.
- Wagtail, Redis, Celery, S3-интеграция и Traefik пока не добавлены.
- Текущая команда Django — runserver; она предназначена для разработки, а не для публичного production-сервера.
- Compose сейчас публикует порты приложения и базы данных. Перед развертыванием в интернете конфигурацию нужно закрыть и разделить на локальную и production.

См. также: [Docker Compose](../docker-compose.yml), [Dockerfile](../Dockerfile), [зависимости](../requirements.txt), [настройки Django](../knowledge_base_project/settings.py).

### Потоки и границы доступа

- Из интернета доступны только TCP-порты **80 и 443**. Порт 80 перенаправляет на HTTPS.
- SSH нужен для администрирования и деплоя; доступ к нему следует ограничить IP-адресом или VPN.
- Django, PostgreSQL и Redis общаются по внутренней Docker-сети. Порты **8000, 5432 и 6379** наружу не публикуются.
- Traefik завершает HTTPS и передает запросы приложению внутри Docker-сети. Его панель управления не должна быть публично доступна.
- Крупные видео и медиафайлы хранятся в S3. Для прямой передачи браузером приложение выдает ограниченные по времени подписанные ссылки.
- Резервные копии базы данных отправляются в отдельное хранилище, не на тот же VPS.

## Параметры VPS

Это начальная оценка для небольшого проекта; фактический размер зависит от одновременной нагрузки, фоновых задач, объема данных и размера базы.

| Назначение | vCPU | RAM | NVMe |
|---|---:|---:|---:|
| Разработка и текущий состав репозитория | 2 | 4 ГБ | 60–80 ГБ |
| Первый production с Wagtail, PostgreSQL и запасом под Redis/worker | 4 | 8 ГБ | 100–160 ГБ |
| Рост нагрузки | 8 | 16 ГБ | По объему базы, логов и временных файлов |

Для текущего каркаса можно начать с **2 vCPU / 4 ГБ RAM**. Для production-состава из схемы рекомендован старт **4 vCPU / 8 ГБ RAM**. Хранение видео в S3 позволяет не увеличивать локальный диск VPS вслед за медиатекой.

Выбирать тариф стоит также по доступности резервных копий или snapshot, качеству NVMe, пропускной способности сети и расположению дата-центра относительно пользователей.

## Этапы внедрения

1. Сохранить удобный локальный Compose для разработки и исправить согласованность переменных PostgreSQL между Compose и настройками Django.
2. Подготовить production Dockerfile: запуск через production WSGI-сервер, сборка статических файлов, непривилегированный пользователь и health check.
3. Добавить Traefik, домен и TLS; закрыть публикацию портов Django и PostgreSQL.
4. Подключить Wagtail и настроить media storage. Для больших файлов — S3-совместимое хранилище и подписанные URL.
5. Добавить Redis и Celery, когда появятся реальные фоновые задачи.
6. Настроить миграции при деплое, проверку доступности, ротацию логов и резервное копирование PostgreSQL с проверкой восстановления.
7. По мере роста вынести PostgreSQL или фоновые задачи на отдельные ресурсы; добавить поиск и аналитику отдельно от основного запроса приложения.

## Контрольные требования перед production

- DEBUG=False; заданы SECRET_KEY, ALLOWED_HOSTS и доверенные HTTPS/CSRF-домены.
- Секреты хранятся на сервере или в хранилище секретов CI/CD и не попадают в Git.
- Firewall не открывает PostgreSQL, Redis, Django и панель Traefik в интернет.
- Данные PostgreSQL находятся в постоянном томе; резервные копии копируются за пределы VPS.
- Проверено восстановление базы из резервной копии.
- Для приложения настроены HTTPS, health check и автоматический перезапуск контейнеров.
